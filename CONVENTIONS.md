# Соглашения кода

Решения о форме кода LATTICE, у которых нет другого дома. У каждой нормы один дом:

| Норма | Дом |
|---|---|
| правило продукта | `docs/design`; кандидат туда — строка Q-NN в `PLAN.md` фазы, решает владелец |
| проверяемая машиной | fitness, тест структуры или eslint (ST-16); норму называет отказ проверки |
| API общего кода | сам код: сигнатуры и комментарий в файле |
| решение о форме без другого дома | пункт этого файла |
| процесс | навык `plan-task` |

Пункт расходится с правилом — прав дизайн (`AGENTS.md`).

**Пункт** — заголовок `### §N.M Название` в разделе `## N.`, следом строка `Область:` — пути, к которым он относится, globs в обратных кавычках. Номер растёт внутри раздела и не переиспользуется: убранный пункт оставляет пропуск. Находка ревью и спор называют пункт — `CONVENTIONS §N.M` (`plan/dev-loop.md`). Форму файла и ссылки на пункты из кода, тестов и процесса держит `plan-check`; пункты читает `plan/tools/dev-loop/conventions.mjs`.

**Правило дописывания.** Соглашение, принятое по ходу задачи, — сначала проверка: тест структуры, fitness-тест или правило eslint, чей отказ называет норму. Пункт сюда — только если проверку написать нельзя: новым номером в конце своего раздела, с областью путей. Пункт, который стал проверкой, уходит отсюда в той же ветке.

## 1. Данные

### §1.1 Записи — замороженные простые данные
Область: `src/**`

Нет класса на тип записи, нет методов на данных, нет прототипов кроме `Object` и `Array` (ST-03). Объект записи — то, что даёт строгий парсер ядра, плюс `Object.freeze`.

### §1.2 Типы `readonly`
Область: `src/**`

Поля `readonly`, массивы `readonly T[]`, словари `{ readonly [key: string]: V }`. Функция не мутирует вход; новое значение — новый объект.

### §1.3 Данные — `type`, поведение — `interface`
Область: `src/**`

Запись, intent, proposal, commit, строка, отказ и строка реестра правил — псевдонимы `type`: так они присваиваются `JsonValue` и идут в `canon` и `hash` без приведения. Порт, read view, команда — `interface`.

### §1.4 `Record` — тип записи
Область: `src/**`, `test/**`

Так называется тип записи в `kernel` (KR-04, ST-03; решение владельца Q-15). Утилита TypeScript `Record<K, V>` в коде не используется — словарь пишется индексной сигнатурой (§1.2).

### §1.5 Заморозка проверяется в тестах
Область: `test/**`

На границе модуля тест передаёт вход через `deepFreeze` (`test/support/deep-freeze.ts`) — функция, которая мутирует вход, падает в тесте. В рабочем коде глубокая заморозка не обязательна: её гарантируют строгий парсер ядра и `readonly`.

### §1.6 Адаптер — фабрика от своих настроек
Область: `src/adapters/**`, `src/ledger/ports/**`

Класс — только у сущности с изменяемым состоянием внешнего мира: адаптер может быть замыканием или классом. Порт — `interface`, адаптер — фабрика `createX(options)` от своих настроек, которая возвращает объект этого интерфейса (решение владельца Q-22).

### §1.7 Имя адаптера начинается с порта
Область: `src/adapters/**`

Адаптер живёт в `src/adapters/<port>-<variant>/` (`store-memory`, `clock-fixed`): по имени тест структуры знает, какой интерфейс адаптеру можно импортировать (ST-01).

### §1.8 Адаптеры для тестов собирает тестовая сборка
Область: `src/adapters/**`, `test/**`

Каждый `*-fixture` (TR-14, LG-23), `clock-fixed` и `ids-counter` (ST-07) собирает только `test/support/assembly.ts`; что ни один файл `src/`, `assembly` тоже, их не импортирует, проверяет тест структуры (решение владельца Q-13, `plan/closure-check.md`, «acts и права»).

### §1.9 Аргументы порта — один объект
Область: `src/ledger/ports/**`, `src/adapters/**`

Операция порта с несколькими аргументами принимает один объект с именами аргументов из правила — у всех портов, без порога: `prepare({request, onto})`, `push({worktree, ref, expected, message, trailers})` (LG-23), `append({commit, delta, evidence})` (LG-02). Операция с одним аргументом берёт его как есть (решение владельца Q-11).

### §1.10 Адаптер store не знает canon
Область: `src/adapters/store-*/**`, `src/ledger/ports/store.ts`

Решения владельца по ревью S0-03, Q-09, Q-19, Q-27: ledger отдаёт в `append` коммит его канонической строкой. Из `commits` и `tail` store отдаёт байты каждой строки, как их хранит, пустую тоже; ledger сам декодирует их (KR-10) и разбирает. Адаптер ничего не декодирует, не разбирает и не выбрасывает, а строкам delta смысла не придаёт (LG-35). Порядок ключей строк — `sortRows`, который порт `store` отдаёт вместе с контрактом (Q-18). Строки, которые оставляет delta, адаптер держит в `keptRows` из порта: она применяет delta так же, как ledger, и отвечает на `row` и `rows`; сам адаптер `from` и `to` не читает.

### §1.11 Подписи и ключи
Область: `src/trust/**`, `src/ledger/**`, `src/cli/**`

G-10, G-24; D-06; кандидат в дизайн — Q-35. Подпись — Ed25519 из `node:crypto`, записанная `ed25519:<base64url без =>` (RFC 4648 §5, 64 байта); публичный ключ — строка OpenSSH `ssh-ed25519 AAAA… [комментарий]` (TR-10). Подписываются UTF-8 байты текста hash `sha256:<hex>` (KR-12): commit — его hash без `sig` ключом land session (LG-06), proposal — его hash без `sig` ключом сессии (LG-10). Подпись или ключ в другом написании не исправляются молча: проверка подписи их не принимает. Функции подписи — `src/trust/signature.ts`, чистые: закрытый ключ сессии приходит параметром, файлы ключей читает `cli`.

### §1.12 Имена — термины LATTICE
Область: `src/**`, `test/**`

Имя понятия — термин `docs/design/00-glossary.md` (ST-03); аналогия — не термин (ST-Z02). Слово, которого нет в глоссарии, — локальная переменная или функция — можно; тип или экспорт с новым смыслом — нет: новый термин входит в дизайн правкой глоссария (GL-Z01).

## 2. Результаты

### §2.1 Нарушение правила — значение, не исключение
Область: `src/**`

Жёсткая проверка возвращает `Result<T>` (`src/kernel/rejection.ts`): список отказов не пуст. Значение успеха — то, что задаёт правило: apply — `commit` или `no-op` (LG-14), landing — свой исход (LG-25).

### §2.2 Значение проверки — проверенное, без приведения
Область: `src/kernel/**`, `src/ledger/**`, `src/codec/**`

Экспортируемая жёсткая проверка `kernel` и `ledger` (S0-37) отдаёт в `T` проверенное значение своего типа, где оно есть. Приведения типа после проверки (`as Commit`) нет: закрытую форму читает `closedForm` (§3.7). Внутри модуля проверки складываются через `rejectionsOf`; отказы сортируют `refuse` и `refused`. Исключение — `validate` (§2.4). Проверка, которая проверяет весь вход от корня, — `apply`, `land`, `openLines`, `openTail` (LG-50, Q-29) — места не берёт; остальные и `parse` кодека берут `Place` (§3.2).

### §2.3 Исключение — только ошибка программы
Область: `src/**`

Исключение — нарушенный инвариант, который вход не мог нарушить, если код верен; сообщение начинается с `bug:`. Сбой внешнего мира в адаптере (диск, сеть, процесс `git`) — тоже исключение: это не нарушение правила. Вход, который правило отклоняет, никогда не приходит исключением и никогда не исправляется молча (KR-10, LG-42).

### §2.4 Нарушения `validate` — не отказ
Область: `src/kernel/**`

Нарушение `validate` (KR-21) — свой тип `{ path, keyword, expected, got }`, не отказ. В отказ KR-21 его переводит один вход ядра для одной записи — `checkAgainstType` (`src/kernel/against-type.ts`, S0-36); тип, который не проходит `readType` и `checkSchema`, для ядра не тип: отказ KR-15, а не исключение (Q-33). Формат внутри схемы (`format: date`) — тоже нарушение KR-21, а не отказ KR-11: отказы правил формата — для проверок вне схемы.

### §2.5 Чистые модули синхронны
Область: `src/**`

`Promise` появляется только на порту; функция, которая ждёт порт (landing, открытие store), асинхронна, всё, что она зовёт между портами, — нет (решение владельца Q-17).

## 3. Отказ

Форма отказа (LG-17), `Place`, `ROOT`, `Result` и функции отказа — `src/kernel/rejection.ts`.

### §3.1 `intent` и `path`
Область: `src/**`

G-13; кандидат в дизайн — Q-36. `intent` — значение `id`, записанное в intent, как есть, даже если оно неверно; так отказ не зависит от порядка intents (LG-11). `path` — JSON Pointer внутри этого intent: `/body/title`, `/expected`. Если у intent нет строкового `id` или отказ не про intent (подпись proposal, сессия, открытие store, загрузка библиотеки), `intent` — `null`, а `path` указывает от корня проверяемого входа: `/intents/3/id`, `/sig`. Корень целиком — `""`.

### §3.2 Место проверки и корень `path` в landing
Область: `src/**`

Решение владельца Q-29; кандидат в дизайн — Q-36. Функция, которая проверяет часть входа, берёт `place` — место этой части во входе — и строит отказы от него (`parseJson(text, place)`, `readProposal(value, place)`, `checkHeader(value, place)`); готовые отказы не переписываются. Вход landing — дерево change request: у отказа с `intent: null` `path` — путь файла в дереве, дальше JSON Pointer внутри него: `/store/proposals/cr-x.json/intents/0/op`, `/store/proposals` (LG-54), `/store/knowledge.jsonl` (LG-23). Строка `store/knowledge.jsonl` — её номер с 1, как `seq`: `/store/knowledge.jsonl/1/seq`; так же — при открытии store на tail `main`. Отказ про intent со строковым `id` остаётся внутри intent (`/op`).

### §3.3 `expected` и `got`
Область: `src/**`

JSON-значения: что правило ждало и что пришло. Описание вместо значения допустимо, когда значения нет: `expected: "a ULID"`, `got: "absent"` у поля, которого нет. У байтов JSON-значения нет — отказ называет их hash `sha256:…` (Q-19). Значение секрета туда не попадает (§6.3).

### §3.4 Отказ создаётся только `reject`
Область: `src/**`

`rule` и `message` берутся из строки реестра. Литерал `"KR-06"` вне реестра — нарушение соглашения.

### §3.5 Реестр правил модуля
Область: `src/**/rules.ts`

Файл `src/<module>/rules.ts` (у адаптера — `src/adapters/<adapter>/rules.ts`): плоский список констант `satisfies Rule`, по одной на rule ID, который применяют жёсткие проверки модуля, и массив `RULES` из них (пример — `src/kernel/rules.ts`). Имя константы — rule ID с `_` вместо `-`. Не фреймворк (ST-02): ни классов, ни регистрации во время выполнения, ни поиска по строке. Один rule ID может стоять в реестрах двух модулей, если правило велит проверять в двух местах (LG-20: landing и recording); повтор той же проверки в другом модуле — обход (`plan/closure-check.md`).

### §3.6 Исключения genesis и store init
Область: `src/ledger/**`

Исключения LG-18 тоже называются rule ID — константами реестра `ledger` в отдельном списке `EXEMPTIONS`, не в `RULES`: исключение ничего не отклоняет, фикстур ST-17 у него нет; показывают его тесты init.

### §3.7 Закрытая форма
Область: `src/kernel/**`, `src/ledger/**`, `src/trust/**`

Объект, у которого каждое поле названо и лишних нет (заголовок record KR-04, тело типа KR-14, `ref` KR-19, commit LG-06, proposal и intent LG-09), читают таблица `MembersOf<T>` и `closedForm` из `src/kernel/closed-form.ts` (S0-35, S0-37); ядро, которому нужно сложить отказы формы с другими, зовёт `closedRejections`. Hash подписанной формы берёт поля из той же таблицы — `unsigned(value, members)` в `src/ledger/commit.ts`. Новая закрытая форма (S0-08, S0-13, S0-16, S0-23) — новая таблица, не своя копия проверки полей.

## 4. Жёсткие проверки и фикстуры

### §4.1 Жёсткая проверка объявляет свои rule IDs
Область: `src/**`

Жёсткая проверка (ST-17) импортирует константы rule IDs из реестра своего модуля и отклоняет только с ними. Правило без жёсткой проверки в реестр не входит.

### §4.2 Фикстура ломает одно
Область: `test/fixtures/**`

Раскладку (`test/fixtures/<RULE-ID>/trigger/` и `pass/`, файл `<case>.json`) и формат (`check`, `input`, `expect`) держат `test/fixtures/coverage.test.ts` и `run.test.ts`; формат описан в `test/fixtures/run.ts`. Сверх них: trigger строится так, чтобы ломать одно, и имя файла говорит, что сломано; pass — минимальный верный вход, а не «вход без этого нарушения». Текстовый вход (`md` для `import-md`, LG-42) — JSON-строка: она хранит байты точно, включая `\r` и отсутствие `\n` в конце.

### §4.3 Вход фикстуры — публичными функциями
Область: `test/fixtures/**`

Строка `checks.ts` готовит вход только публичными функциями модулей: предыдущее состояние store — список proposals, проведённых через apply по очереди; commit, собранный руками в обход apply, — обход (`plan/closure-check.md`, «запись знания»). Сырое дерево и сырые строки store, которых не пишет landing, — только во входе trigger (Q-23).

### §4.4 Проверки landing — через `land`
Область: `test/fixtures/**`

S0-33. Проверку со склейкой вокруг фикстура видит только целиком: строка `land` в `checks.ts` прогоняет `land(…, {dryRun: true})` на `git-fixture`, собранном тестовой сборкой из `input.branches`; `commit` и `no-op` — принят, `rejections` — отклонён, другой исход — ошибка фикстуры. Чистые проверки без склейки — JSON-текст, значение proposal, apply, строки store — идут без `land`.

## 5. Порядок

Порядок всего, что видит человек или что пишется в байты, — детерминированный и не зависит от порядка входа, окружения и обхода `Map`. Кандидат в дизайн для §5.1–§5.3 — Q-34.

### §5.1 Нарушения `validate`
Область: `src/kernel/**`

KR-21: по `path`, затем по `keyword`, затем по каноническому JSON `expected`, затем `got`.

### §5.2 Отказы
Область: `src/**`

Отказы apply и других жёстких проверок: по `intent` (`null` первым), затем по `path`, затем по `rule`, затем по `id`, затем по каноническому JSON `expected`, затем `got`. Внутри фазы apply собирает все отказы и сортирует их один раз на выходе фазы (LG-16).

### §5.3 Записи коммита и intents proposal
Область: `src/ledger/**`

LG-06, LG-10, G-03: три группы по очереди — сущности по `id`, факты по каноническому JSON ключа (поля аннотации `key` типа, KR-19, TR-28), прочие события по `id`; при равном ключе решает `id`. Records коммита идут в порядке intents (`canonicalIntents`), hash proposal считается по нему же. Какой intent — факт, знает тип: порядок берёт функцию `KeyOf`; пока apply не читает типы из `before` (S0-13), ни один intent не факт (`NO_FACTS`).

### §5.4 Сравнение строк — по кодовым единицам UTF-16
Область: `src/**`

`a < b` — `compareText` ядра, как сортирует ключи canon (RFC 8785). `localeCompare` и `Intl` не используются: они зависят от локали.

### §5.5 Порядок `Map`, `Set` и `Object.keys`
Область: `src/**`

Это порядок вставки; там, где он доходит до байтов или вывода, явная сортировка обязательна (риск R6 плана S0).

## 6. Сообщения

### §6.1 Сообщение — из шаблона по rule ID
Область: `src/**`

TR-40: шаблон — строка `message` в строке реестра; `reject` подставляет поля отказа в плейсхолдеры `{intent}`, `{path}`, `{expected}`, `{got}`, `{id}` каноническим JSON. Сообщение не собирается конкатенацией в коде проверки и в систему не возвращается: ни один код не разбирает `message`, агент читает `rule`, `path`, `expected`, `got` (AG-04).

### §6.2 Язык — параметр вывода
Область: `src/cli/**`, `src/assembly/**`

`reject` пишет `message` на `en`; `cli` по запросу читателя перерисовывает сообщение на его язык функцией `render(rule, rejection, lang)` из того же шаблона, при отсутствии шаблона языка — `en`. Таблицу правил всех модулей для `cli` собирает `assembly` из их `RULES`. В S0 шаблоны только `en`.

### §6.3 Секрет не повторяется
Область: `src/**`

LG-20: значение секрета видит только проверка секретов; её отказ — `got: null`, а `path` указывает, где секрет. Ни один шаблон не выводит значение, прочитанное через `$env`.

## 7. Чистота

Что запрещено в чистом коде вне `adapters`, `assembly` и `cli` (ST-04, KR-02) — время, случайность, окружение, сеть, файлы, планировщик, локаль, исполнение кода, GC, `console` и состояние на уровне модуля, — держит тест структуры: список и разрешённое — `test/structure/audit-purity.ts`.

### §7.1 JSON — строгий парсер и canon ядра
Область: `src/**`

В `kernel`, `trust`, `ledger` JSON — только через строгий парсер и canon ядра; `JSON.parse` и `JSON.stringify` вне них — нарушение (KR-10). JSON разбирает одна функция — `parseJson` в `src/kernel/parse.ts` (S0-04, D-04); канонический текст пишет одна функция — `canon`, hash считают `hash` и `hashRecord` ядра. Значение, которое ledger знает каноническим, — коммит, сформированный после фазы 1 apply, или прочитанный из канонической строки, — раскрывает `known` в `src/ledger/commit.ts`: отказ там — ошибка программы `bug:`. Адаптеры JSON ledger не разбирают вовсе (§1.10).

### §7.2 Тесты и скрипты — не чистый код
Область: `test/**`, `scripts/**`

Им можно время и случайность, скриптам — `node:fs`, но рабочий код они вызывают так же, как `assembly`. Файлы и программы тест берёт через хелперы `test/support/` — это держит тест структуры (ST-18).

## 8. Файлы и стиль

Импорты по матрице ST-01, входы модулей, списки `kernel-files.txt` и `skeleton-files.txt`, именованные экспорты и английский язык `src/` держит тест структуры; профиль качества — `eslint.config.js` (Q-08); `nodenext` требует суффикс `.js` в импорте.

### §8.1 Файлы и точка входа модуля
Область: `src/**`, `test/**`

Файлы — `kebab-case.ts`. Точка входа модуля — `src/<module>/index.ts`; соседние модули импортируют только её и названные входы `test/structure/modules.ts`.

### §8.2 Команды
Область: `src/cli/**`

RT-32: таблица — `src/cli/commands.ts`, текст — из RT-Z03; команда без обработчика названа в `src/cli/stubs.ts` с задачей, где появится. Задача, которая реализует команду, убирает её строку из `stubs.ts` и добавляет обработчик в `src/cli/run.ts`; таблицу не трогает. Код выхода: `0` — сделано, `1` — отклонено (отказы, `moved`, `conflict`), `2` — не запущено (использование, неизвестная команда, заглушка, нет store).

### §8.3 Комментарий объясняет, почему
Область: `src/**`, `test/**`, `scripts/**`

Идентификаторы, комментарии и строки сообщений — на английском (PR-14). Комментарий объясняет, почему, и называет rule ID, если код его исполняет.

### §8.4 Раскладка и имена тестов
Область: `test/**`

Тесты лежат в `test/`, раскладка повторяет `src/`: `test/<module>/…test.ts`; свойства fast-check — там же, рядом с тестами модуля. Название теста, который показывает правило, начинается с его ID: `it("KR-06: refuses …")`. Порты — контракт-тестами в `test/contract/` на всех адаптерах (ST-07); контракт-тест импортирует адаптеры, которые проверяет.

### §8.5 Прогон тестов — функция входа
Область: `test/**`

S0-41; RT-21. fast-check берёт один seed на прогон — `LATTICE_SEED` или фиксированный `DEFAULT_SEED` (`test/support/setup.ts`); свой `seed` в параметрах теста не ставится, кроме выборки, которая проверяет сам генератор (`fc.sample(…, { seed })`). Бюджет свойства — число случаев: `numRuns` у каждого `fc.assert` и `fc.check` (проверяет `test/support/budget.test.ts`). Время — только страховка выше бюджета (`SAFEGUARD_MS` из `test/support/budget.ts`); тест, которому нужно больше, называет свой таймаут явно.
