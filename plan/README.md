# План работ LATTICE

Рабочий план реализации по срезам из [14 Slices](../docs/design/14-slices.md). Это не корпус: LATTICE эти файлы не читает, поэтому они на русском (PR-14, TR-40). Термины LATTICE и ID правил пишутся как в дизайне.

## Где что лежит

```text
plan/
├── README.md                    ← этот файл: устройство плана и правила ведения
├── STATUS.md                    ← доска фаз: какая в работе, какая выполнена
├── closure-check.md             ← проверка замыкания механизмов: нет нового механизма и обхода (RM-08)
├── bench/
│   └── questions.md             ← реальные вопросы о дизайне для первого bench set (SL-08)
├── phases/
│   └── S0-kernel-ledger/        ← одна папка на фазу; создаётся, когда фазу начинают планировать
│       ├── PLAN.md              ← план фазы: объём, этапы, граф, риски, вопросы, критерии готовности
│       ├── STATUS.md            ← доска задач фазы: статус, PR, заметка
│       ├── RULES.md             ← генерируется: каждое правило фазы → задачи
│       └── tasks/
│           └── S0-NN-<slug>.md  ← одна задача — один файл
└── tools/
    └── plan-check.mjs           ← проверка согласованности плана
```

Почему не `docs/`: после переключения (SL-03) `docs/` — только экспорт из ledger, и ручная правка валит CI (LG-43). План живёт рядом, а не внутри.

## Единственный источник правды

| Что | Где | Не дублируется в |
|---|---|---|
| статус фазы | `plan/STATUS.md` | плане фазы |
| задача в работе, на ревью, в блоке | её PR на GitHub (draft, ready, метка `blocked`) | доске |
| итог задачи и ссылка на PR | `phases/<фаза>/STATUS.md` | файле задачи |
| содержание задачи, зависимости, правила, модули | frontmatter и текст файла задачи | доске |
| соответствие «правило → задача» | frontmatter задач (`rules`) | — `RULES.md` только генерируется из него |
| открытые вопросы фазы и решения по ним | `phases/<фаза>/PLAN.md`, раздел «Вопросы» | задачах (там — ссылка `Q-NN`) |
| решения по дизайну | `discussion/decisions.md`, затем правка `docs/design` | плане |

## Статусы

| Фаза | Значение |
|---|---|
| ⬜ не начата | план фазы ещё не составлен |
| 📝 план | план готов, реализация не начата |
| 🔄 в работе | идёт реализация |
| 🔍 приёмка | все задачи готовы, владелец проверяет командой приёмки (SL-01) |
| ✅ выполнена | проверка фазы зелёная в CI, владелец принял |

Задача на доске `main` — только итог: он приезжает вместе с merge её PR, потому что `main` меняется только через PR.

| Задача | Значение |
|---|---|
| ⬜ не сдана | PR нет или он ещё открыт |
| ✅ готово | PR влит; в колонке — ссылка на него |
| ✖ отменена | задача снята или поглощена другой; причина — в файле задачи |

Что сейчас в работе — открытые PR задач: draft — в работе, ready — на ревью, метка `blocked` — ждёт ответа владельца. Одновременно открыто не больше трёх (SL-06): `gh pr list`.

## Как вести

- **Выполнение задачи** — от доски до PR — по навыку [plan-task](../.claude/skills/plan-task/SKILL.md); человек вызывает его как `/plan-task S0-04`, агент приходит к нему из `AGENTS.md`.
- **Правка самого плана** — затем `node plan/tools/plan-check.mjs`; после изменения `rules` в задачах — `node plan/tools/plan-check.mjs --rules`, чтобы обновить `RULES.md`.

## Нумерация

- Задача: `<фаза>-<NN>`, например `S0-04`. Номер никогда не переиспользуется и не перенумеровывается, как ID дизайна (RM-02). Отменённая задача остаётся файлом со строкой «Отменена: причина» и статусом ✖ на доске.
- Вопрос фазы: `Q-NN` внутри плана фазы.
- Файл: `S0-04-canon-hash.md` — ID, затем короткий slug.

## Проверка плана

`node plan/tools/plan-check.mjs` проверяет:

- frontmatter задач, совпадение ID с именем файла, существование зависимостей, отсутствие циклов;
- что доска фазы и файлы задач совпадают один к одному, статусы из списка выше, названия совпадают;
- что задача ✅ не зависит от незавершённых;
- что каждое правило фазы (по таблице SL-Z04) отнесено хотя бы к одной задаче, а правила в `rules` существуют в дизайне;
- что `RULES.md` не устарел.

И печатает сводку: прогресс, готовые к старту задачи, критический путь, задачи-триггеры аудита (ST-15). О PR инструмент не знает: «готова к старту» задача, у которой может уже быть открытый PR, — это видно в `gh pr list`.
