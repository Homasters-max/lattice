# Проверка замыкания механизмов

Механизм вне реестра RM-Z04 не существует (RM-08, PR-03). Проверка соответствия идёт от правила к коду и не видит кода, о котором правила молчат, — новый механизм и обход живут именно там. Эта проверка идёт обратно: **от кода к реестру**.

| Где | Объём описи | Кто |
|---|---|---|
| каждый PR | добавленные и изменённые экспорты, скрипты, тест-хелперы, которые строят записи | исполнитель до PR, ревьюер в PR |
| триггер аудита ST-15 | модули, которые задел триггер | аудитор |
| конец среза (ST-14) | весь `src/`, `scripts/`, тест-хелперы `test/` | аудитор (S0-30) |

## Термины

- **Механизм** — код, от поведения которого зависят другой код или сохранённые байты и который решает, как запись пишется, упорядочивается, идентифицируется, допускается или отклоняется, читается со смыслом, кешируется или индексируется, исполняется. Список механизмов — RM-Z04.
- **Обычный код** — тело внутри механизма: функции, структуры данных, разбор (PR-06).
- **Обход** — второй путь к результату, которым уже владеет механизм из RM-Z04.

## Шаги

1. **Опись.** Выписать каждую единицу из объёма таблицы выше: экспорт модуля, файл `scripts/`, тест-хелпер, который строит записи.
2. **Тест удаления** для каждой строки описи — что пропадёт, если её удалить:
   - перестаёт выполняться правило — строка принадлежит механизму этого правила, вердикт — строка RM-Z04;
   - пропадает поведение, которого не описывает ни одно правило, — **новый механизм**, находка;
   - ничего наблюдаемого — обычный код (или мёртвый — удалить).
3. **Каталог обходов** ниже — каждый класс против описи.
4. **Отвергнутое** — NX-01…NX-27 в [15-later](../docs/design/15-later.md): ни одна отвергнутая идея не вернулась под другим именем.
5. **Итог.** Готово, когда у каждой строки описи есть вердикт (строка RM-Z04, обычный код или находка) и каждый класс каталога отмечен «нет» или находкой. В PR — раздел «Замыкание»: «новых механизмов и обходов нет» или список находок. Находка останавливает работу: новый механизм появляется только правкой дизайна — строкой RM-Z04 и правилом с ID (RM-08), по решению владельца.

## Каталог обходов

| Класс | Владелец | Признак обхода |
|---|---|---|
| запись знания | apply внутри landing (PR-02, LG-14, LG-22) | запись в store или `store/knowledge.jsonl` мимо landing; скрипт или тест-хелпер, который строит commit без apply |
| порядок | `seq` (LG-04, KR-08) | порядок из `at`, из порядка массива, из времени файла |
| идентичность и hash | canon (KR-06, KR-10, KR-12) | `JSON.stringify` или своя сортировка ключей вместо canon; hash не от канонических байтов; id, придуманный apply |
| отказ | жёсткая проверка с rule ID (ST-17, LG-17) | исключение вместо отказа; отказ без rule ID; проверка правила, повторённая в другом модуле; вход, молча исправленный там, где правило его отклоняет (KR-10, LG-42) |
| отключение проверки | такого механизма нет | параметр или флаг вида skip, force, unsafe; ветка по окружению или по «режиму теста» в чистом коде |
| исключения | реестр исключений по rule ID (LG-18) | исключение, выведенное из ключа, имени или «это genesis» без rule ID |
| производные данные | fold и проекции (PR-04, LG-34) | кеш, индекс, реестр, memo или изменяемое состояние модуля вне fold (NX-05, NX-06) |
| смысл проекции | одна функция fold (LG-35) | смысл, посчитанный в адаптере store или в SQL (NX-20) |
| чтение ledger | read view (LG-38) | чтение строк store мимо view из apply, checks или codec |
| время, id, внешний мир | порты и адаптеры (ST-04, LG-23) | `Date`, случайность, окружение, файлы в чистом коде |
| acts и права | порт `acts`, фаза 5 (TR-14…TR-17) | act, засчитанный не через порт; `acts-fixture` в рабочей сборке `assembly` |
| версия | версия, закреплённая в `before` (LG-53) | landing исполняет код change request |

**Не обход** — разрешено правилом: сырые коммиты для проверки тотальности fold (LG-36) — только в `test/` и с пометкой; кеш fold библиотек в `.lattice/` (LG-45); dev-скрипты сборки `std` и пересборки из дизайна (S0-24, S0-29) — когда они идут через публичные команды `lattice`.

## Ratchet

Находка, которую код может проверить, становится fitness-тестом, иная — правилом с ID (ST-16). Кандидаты, которые стоит сделать тестами сразу, как появится код:

- путь `store/knowledge.jsonl` встречается только в адаптере `store-jsonl`;
- значение `Commit` создаётся только в `ledger` (branded type);
- отказ создаётся только конструктором из реестра правил;
- в `kernel`, `trust`, `ledger` нет `JSON.parse` и `JSON.stringify` вне строгого парсера и canon;
- в чистых модулях нет изменяемого состояния на уровне модуля: `let` и мутируемые `Map`, `Set`, массивы вне функций;
- `assembly` подключает адаптеры `*-fixture` только в тестовой сборке — тест структуры с S0-03: адаптеры для тестов собирает `test/support/assembly.ts`, ни один файл `src/` их не импортирует (ST-07, Q-13);
- `scripts/` импортирует только `cli`.
