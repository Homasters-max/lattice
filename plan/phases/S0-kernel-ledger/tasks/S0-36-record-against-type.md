# S0-36 · Запись против своего типа — один вход фазы 2 и чтение схемы

## Зачем

Архитектурный разбор, волна 2 (2026-10-07). У понятия «запись против своего типа» — фазы 2 apply (LG-16: тела типов и `extends`, тело против `type@n`, KR-14…KR-22) — нет модуля:
- **Фаза 2 сшивала бы шесть экспортов сама.** `checkRev(kind)`, `checkRecordType`, затем `checkType`, если тип — `core/type@1`, иначе `checkBody` (G-26). Вид и схему из тела типа читает `readType`, но `index.ts` его не экспортирует — ledger читал бы тела типов заново.
- **Резолверов два.** `Resolve` (ref → Schema) и `ResolveType` (ref → тело типа): `compare` переводит один в другой внутри (`compare.ts:149`), `checkBody` заставляет делать это вызывающего. Тесты собирают оба руками: `resolveFrom` и `typesFrom` в `checks.ts`, `compare.property.test.ts`, `type.test.ts`, `compare.test.ts`.
- **Инвариант не в интерфейсе (Q-33).** `readType` проверяет форму тела типа, но не то, что его схему допускает `checkSchema`. `checkType` с родителем `{type: "array", const: [1], items: 5}` бросает `bug: validate takes a schema checkSchema admits; items is no schema` — исключение вместо отказа (каталог обходов `plan/closure-check.md`, класс «отказ»).

У всего, что сделали S0-06 и S0-07 (`checkType`, `checkSchema`, `checkBody`, `validate`, `compare`, `checkRev`, `checkRecordType`), нет вызова в рабочем коде — только тесты и `checks.ts`. Первый настоящий вызывающий — S0-13; до него форма интерфейса меняется дёшево.

Заодно — **чтение схемы** (разбор, кандидат 5): что значит схема, разбросано по `schema.ts`, `validate.ts`, `compare.ts`, `compare-values.ts`, `compare-annotations.ts`. Ветка union по `const` дискриминатора написана трижды (`schema.ts:159`, `validate.ts:152`, `compare.ts:64`); `typesOf` дважды с разным смыслом (`schema.ts:69`, `compare-values.ts:14`); списки типов и форматов дважды (`schema.ts:19-21`, `validate.ts:42-59`), а `Format` в `formats.ts` не знает `ref` и `uri`; regex ключа словаря `validate.ts:112` равен `SEGMENT` в `ref.ts:28`; помощник `number` дважды (`validate.ts:67`, `compare-values.ts:29`); `properties` и `required` читаются inline в четырёх местах. S0-15 (ссылки и метки) и S0-18 (эволюция) будут читать схемы ещё раз.

## Объём

Входит:
- **один вход ядра для фазы 2 одной записи**: `rev` по виду её типа (KR-04), запись abstract типа (KR-16), для `core/type@1` — meta-type и цепочка `extends` с `compare` (KR-14, KR-15, KR-22, G-26), иначе — тело против схемы типа (KR-21). Заголовок, канон и форматы — фаза 1 (`checkHeader`), сюда не входят;
- **один резолвер** — тел типов по pinned ссылке (`ResolveType`): ядро само читает схему из тела типа; `Resolve` становится внутренним;
- **тип, прочитанный ядром, — проверенный** (Q-33): для каждого типа, до которого дошёл резолвер (глубина ≤ 4, KR-15), ядро проверяет его тело (`readType` и `checkSchema`), а не доверяет резолверу. Тип, который не проходит, — отказ KR-15 на `/extends` (для родителя) или на `/type` записи, `expected: "an admitted type"`, а не исключение;
- **экспорты**: `checkRev`, `checkRecordType`, `checkType`, `checkBody` и `Resolve` уходят из `index.ts` внутрь ядра; `validate` (свой тип нарушений KR-21, CONVENTIONS §2), `checkSchema` и `compare` (S0-18, режим `revision`) остаются; экспортируется тип результата `compare`;
- **чтение проверенной схемы** — внутренний модуль ядра: типы, поля и `required`, вложенные схемы, ветка по тегу. `validate`, `compare`, `checkSchema` и `checkType` его только потребляют; копии из «Зачем» удаляются, `Format` получает `ref` и `uri`, regex ключа словаря берётся из `ref.ts`.

Не входит:
- закрытая форма тел (KR-14, KR-19) — S0-35, задача берёт её готовой;
- форма результата (`Result` вместо `Rejection[]`) — S0-37;
- подключение к apply — S0-13.

## Интерфейс

Набросок; точную форму выбирает задача.

```ts
// src/kernel/<file>.ts — фаза 2 одной записи (LG-16)
checkAgainstType(record: Record, resolve: ResolveType, place: Place): Rejection[]
// resolve: тело типа по pinned ссылке из `after` (LG-11: тип и его блоки — в одном коммите); null — неизвестен
```

## Шаги

1. Тесты нового входа через `index.ts`: запись entity без `rev` и event с `rev`, запись abstract типа, тело против схемы, тело типа (`core/type@1`) с цепочкой `extends`, родитель с недопущенной схемой (Q-33), неизвестный тип. Красные.
2. Вход и чтение типа через проверку; `bug:` на недопущенном родителе уходит.
3. Внутренний модуль чтения схемы; `validate`, `compare`, `checkSchema` переходят на него.
4. Экспорты `index.ts` сужаются; тесты ядра и `checks.ts` переходят на новый вход.

## Тесты и фикстуры

- `KR-15/trigger/parent-not-admitted` — родитель, схему которого `checkSchema` не допускает; отказ KR-15 на `/extends`, без исключения (Q-33). К ней — `KR-15/pass/parent-admitted`.
- Строки `body`, `type` и `record-type` в `checks.ts` сводятся к одной строке `record`: вход — запись и тела типов по ссылкам. Фикстуры KR-04 (rev по виду), KR-14…KR-16, KR-21 переходят на неё; `rule` ожиданий не меняется, `path` получает место записи — смена входа строки, как у LG-23 в S0-32, а не правила. Строка `schema` (KR-18, KR-19) остаётся.
- Свойство: схемы property-тестов `compare` генерируются через `checkSchema` — недопущенная схема в них не попадает.
- `compare.property.test.ts` (`validate` против `compare`) зелёный без правки.

## Риски и заметки

- **Q-33** — решение владельца 2026-10-07 (PLAN.md, раздел 11).
- **Стоимость проверки родителя.** `checkSchema` для каждого типа цепочки (≤ 4, KR-15) на каждую запись — это дёшево для S0. Если на корпусе (S0-26) это заметно, кеш — не в ядре: только fold и проекции держат производные данные (PR-04, `closure-check.md`); решение — вопрос владельцу.
- **Файлы ядра.** Новые и удалённые файлы — строки `test/structure/kernel-files.txt` (ST-05; по R9 не файл skeleton). Внутреннее деление `compare` (`compare-shown`) не трогается.
- S0-08 и S0-13 зависят от этой задачи: S0-08 проверяет типы S0 этим входом, S0-13 — первый вызывающий фазы 2.
