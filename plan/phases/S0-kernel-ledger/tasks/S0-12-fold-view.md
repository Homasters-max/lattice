# S0-12 · Fold, проекции, read view и verify-store

## Зачем

Одна чистая функция fold держит смысл всех проекций (LG-35); read view — единственный способ, которым apply, checks и потом runtime читают ledger (LG-38). Второй критерий готовности S0 — rebuild равен строкам (LG-37) — проверяется здесь.

## Объём

Входит:
- **`fold(view, commit, evidence) → delta`** (LG-35): delta — строки, которые commit открывает и закрывает; строка — канонический JSON с `from` и `to`; без часов, id и порядка параллельного обхода; evidence в S0 не декодируется — fold принимает его, но run из него не читает;
- **fold тотален** (LG-36): висячая ссылка или дубликат сворачиваются как есть;
- **проекции S0** (LG-34): текущая и последняя ревизии и каждая ревизия, referrers по ссылкам и внешним ссылкам (RF-09), держатель уникального значения (LG-19 — строка; проверка — S0-15), процитированное evidence; строки standing — каркас: ключ и вопрос есть, строки и правила приходят из S0-14; до S0-14 текущая ревизия — записанная последней;
- **ссылки и уникальные значения тела** читает обход тела по схеме его типа — `valuesOf` ядра (`src/kernel/values-of.ts`): `$ref`, ветка union, items, values и поля, как обходит `validate`; тип берётся из того же коммита или из view (LG-11);
- **ключи строк**: префиксы по видам проекций, детерминированная сортировка; схема ключей — в коде, `KEYS` и функции ключей `src/ledger/rows.ts` (API кода живёт в коде, не в `CONVENTIONS.md`);
- **read view** (LG-38): `seq`, `current(id)`, `latest(id)`, `revision(id, n)`, `referrers(target, label?)`, `holder(unique)`, `standing(ref)`, `blocks(types, namespaces)`, `evidence(hash)`; `view(seq)` — строки с `from ≤ seq` и `to` пустым или больше; `tuple` — S1; форма `holder` и `blocks` — G-53;
- view — интерфейс, который можно составить из нескольких: своего fold и fold библиотек (S0-22);
- **лента и view на любой `seq`** (LG-41): `feed(from)` и `viewAt(seq)` открытого store;
- **`lattice verify-store <путь>`** (RT-32): открыть `jsonl` store каталога той же операцией, что `openTail`, проверить цепочку и пересобрать строки с genesis; подписи — с S0-20: до неё `verify-store` открывает store без ключей, как `openTail` (Q-39, G-51), и вывод не утверждает их проверку; команде нужна сборка без портов — `verifyStoreAt` в `assembly`. Сравнить пересборку в S0 не с чем: `memory` и `jsonl` не хранят строк между открытиями — равенство пересборки строкам, накопленным коммит за коммитом (LG-37), показывает property-тест; сравнение с хранимыми строками — со store, который их хранит (`postgres`, S1).

## Тесты и фикстуры

LG-39: rebuild с genesis равен строкам, накопленным коммит за коммитом (property-тест на случайных последовательностях коммитов); каждый вопрос view на `memory`; fold тотален на коммитах, которые apply отклоняет; позже, в S0-13, — `after` apply равен `view(seq)` store после landing.

## Готово, когда

- [x] property-тест LG-37 зелёный; строки — канонический JSON, порядок не зависит от обхода
- [x] все вопросы read view S0 отвечают на `memory` и `jsonl` одинаково
- [x] `lattice verify-store <путь>` работает на `jsonl` и печатает итог
- [x] fold не бросает исключений ни на одном входе из фикстур отказов

## Риски и заметки

- R6 — главный риск: `Map` и `Object.keys` не используются для порядка вывода без явной сортировки.
- Если задача растёт сверх L — делить на «fold и строки» и «read view и `verify-store`».
- От архитектурного разбора, волна 2 (2026-10-07): read view и rows сейчас разложены по шести местам — `view.ts` (13 строк, вход ST-01), `rows-view.ts` (21, проход насквозь: `View` определён в нём и реэкспортирован `view.ts`, импортируется по обоим путям), `rows.ts`, `fold.ts`, `keptRows` в `ports/store.ts`, `openLines` в `tail.ts`. S0-11 сводит rows в один модуль; эта задача строит fold и вопросы view на нём, а `verify-store` открывает store той же операцией, что `openTail` («строки → проверенный tail», S0-11).
- От S0-11: rows — один модуль `src/ledger/rows.ts`: `Row`, `Delta`, `View`, `withDelta` (закрытие строки, которой нет, — `bug:`), `held`, `viewOf`, `sortRows` и `keptRows` порта; вход `ledger/view` реэкспортирует `View`. Открытие store — `openLines(lines, keyOfSession)` и `openStore(store, keyOfSession)` в `src/ledger/chain.ts`: разбор канонических байтов строки (`parseCanonical` ядра, KR-10), форма, цепочка и подписи, fold с genesis и передача строк адаптеру (`Store.keep`). `verify-store` зовёт `openStore` с ключами сессий; fold при открытии пока получает пустой список evidence.
- Сделано иначе, чем в наброске: задача задела `kernel` (обход `valuesOf`; ключи строк пишет `canon` ядра, а части ключа, которые canon отклоняет, — их нет ни в одном коммите, KR-10 — ключа не дают, так fold тотален и на неканоническом входе) и `assembly` (`verifyStoreAt`: `cli` импортирует только `assembly`, G-15) — четыре модуля, триггер аудита ST-15; схема ключей — в коде; набросок велел проверять подписи `verify-store` ключами land sessions из самого store — ревью (W1-A1) сочло это обходом trust, и по решению владельца (G-51) до S0-20 `verify-store` подписей не проверяет, источник ключа решает S0-20; семантика referrers — G-52. Набросок требовал от `verify-store` сравнить пересобранные строки с накопленными (LG-37); строки, которые `jsonl` отдаёт через порт, — те же, что ledger передал ему при открытии, и сравнение с ними ничего не проверяло (ревью, W1-A2, W1-S1): в S0 `verify-store` только пересобирает и не называет LG-37, LG-37 показывает property-тест `test/ledger/fold.property.test.ts`, сравнение с хранимыми строками — S1.
