# S0-09 · Черновики всех схем std — проверка подмножества до заморозки ядра

## Зачем

SL-03 (2): к переключению подмножество схем покрывает каждый тип `std`, который называет дизайн, и ядро замораживается как `1`. Если какой-то тип не выражается подмножеством KR-18, после заморозки это будет новая версия ядра (KR-03, LT-01). Пока ядро `0`, такой пробел дешёвый (R4).

## Объём

Входит — черновики оставшихся типов, проверенные ядром:
- `pipeline` (RT-01, пример RT-Z02), `decision-point` (DP-01, пример DP-Z05), `bench-item` (BN-01, BN-03), набор bench (BN-02, BN-04 — `salt`), `review-note` (TY-04);
- status facts `live`, `calibration`, `verdict`, `dismissed` (TR-29) с ключами по таблице TR-29, `report` (BN-11), `source-listing` (TR-39);
- события `runtime`: `step` (OB-02), `link` (OB-01), `run` и записи tape (RT-14, RT-23), `question` (RT-18), `delivery-intent`, `delivery-attempt` (RT-26), `code-commit` (OB-08);
- **отчёт о пробелах**: что не выразилось или выразилось натянуто, с предложением — правка типа, правка дизайна или (крайний случай) ключевое слово ядра до заморозки.

Не входит: сборка этих типов в ledger `std` (SW), их семантика.

Как сделано:
- исходники — `std/source/<slug>.json`; описание каждого поля, которое держится на пробеле, называет его `G-NN`; тест — `test/ledger/std-types.test.ts`, примеры — `test/ledger/examples/std/<slug>.json`;
- `decision-point` из S0-08 получил поля DP-01 и стал не abstract: DP-Z05 пишет его записи (G-39);
- имена, которых дизайн не даёт: запись ленты — `tape-entry`, набор bench — `bench-set`, форма DecisionResult — abstract `decision-result`, на неё ссылается `run` через `$ref` (G-42);
- примеры дизайна тест читает из `docs/design` как есть: DP-Z05 валиден; RT-Z02 отклоняется только на `params` стадий (G-38); DP-Z07 — шаблон, тест сверяет его альтернативы с черновиком и проверяет каждый статус, заполненный по шаблону;
- тест KR-01 читает имена `std` только из `std/source/`, а тест структуры проверяет, что исходник есть у каждого имени TY-Z02…TY-Z05;
- отчёт — `plan/phases/S0-kernel-ledger/std-schema-gaps.md`, пробелы — G-38…G-44; по G-38 владелец решил (2026-10-08, PR #54): ключевое слово ядра до заморозки — задача [S0-53](S0-53-any-value-keyword.md); она же делает RT-Z02 валидным по черновику `pipeline`.

## Шаги

1. По типу на файл в `std/source/` с пометкой «черновик»; тест на каждый: запись `core/type@1` с телом типа проходит `checkAgainstType` (S0-36).
2. Пример записи из примеров дизайна (RT-Z02, DP-Z05, DP-Z07) проходит `validate`.
3. Отчёт `plan/phases/S0-kernel-ledger/std-schema-gaps.md`; пробелы — в PLAN.md, раздел 12, и вопросом владельцу, если нужна правка дизайна.

## Готово, когда

- [ ] у каждого типа, который называет дизайн, есть черновик схемы, проходящий проверку ядра
- [ ] примеры из дизайна DP-Z05 и DP-Z07 валидны по своим черновикам; RT-Z02 — в [S0-53](S0-53-any-value-keyword.md) (G-38)
- [ ] отчёт о пробелах подмножества готов и разобран с владельцем

## Риски и заметки

- Тест KR-01 (`test/structure/repo.test.ts`) берёт имена `std` из `std/source/` (S0-08) и, пока у типов этой задачи нет исходников, ещё из TY-Z02…TY-Z05 (`designTypeNames`): когда `std/source/` держит каждый тип, который называет дизайн, чтение дизайна можно убрать.
- Задача подготавливает SW и может перейти в SW, если S0 упирается в сроки; приёмку S0 она не блокирует (S0-29 от неё не зависит).
