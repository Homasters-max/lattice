# Задача плана

Одна задача — одна change unit — одна ветка — один PR (PR-15). Аргумент — ID задачи. Без аргумента предложи владельцу первую из «готовы к старту» по `node plan/tools/plan-check.mjs` и начни после его ответа.

Живое состояние задачи — её PR на GitHub: draft — в работе, ready — на ревью, метка `blocked` — блок. Доска фазы на `main` получает итог — ✅ и ссылку на PR — вместе с merge.

## Шаги

В `/dev-loop` шаги 1 и 6 механические и их делает `dl`: `dl start` — ветку, коммит `S0-NN: start` и draft PR; `dl ready` — отметки, доску, фазу, `plan-check` и перевод PR в ready по пунктам, которые исполнитель назвал выполненными (`plan/dev-loop.md`, executor). Вне цикла — как здесь.

1. **Взять.** Задача годится, когда на доске она ⬜, все её `depends` ✅, открытых PR задач меньше трёх (`gh pr list`, SL-06) и ни один из них не меняет тот же контракт (PR-17). Ветка `s0-NN-<slug>` от свежего `main`, пустой коммит `S0-NN: start`, draft PR в `main` с заголовком `S0-NN · <название задачи>`. Готово: draft PR открыт.

2. **Понять.** Прочитай файл задачи, затем вопросы `Q-NN` и пробелы `G-NN` из `PLAN.md` фазы, на которые он ссылается, затем текст каждого правила из `rules` в `docs/design` и правил, без которых он неясен. Готово, когда в описании PR для каждого правила из `rules` записано, чем оно будет показано: фикстурой, тестом или границей ревью (ST-13). Неясное правило — вопрос владельцу до кода.

3. **Тесты первыми.** Для каждого rule ID жёсткой проверки — фикстуры trigger и pass (ST-17); векторы, контракт-тесты портов и свойства — как велит раздел задачи «Тесты и фикстуры». Готово: новые тесты *красные* и падают по той причине, которую проверяют.

4. **Реализовать** в пределах *объёма* задачи; всё, что расходится с её файлом, — по разделу «Отступления». Задача растёт сверх L — стоп и предложение деления по тесту независимости (PR-16): по контрактам, не по слоям (SL-05). Готово: тесты шага 3 зелёные.

5. **Проверить.** `npm run prove` зелёный: затронутые test-sets и весь fitness; итог — `outcome` в JSON последней строки и код выхода, вывод не режется `| tail`. Полный прогон `npm run verify` — для CI и владельца. Проверка замыкания по `plan/closure-check.md` на diff ветки — у каждой строки описи вердикт. «Самопроверка» из `plan/dev-loop.md` на diff ветки. Отметь триггеры аудита ST-15: правка файла из `test/structure/skeleton-files.txt`, новый модуль или порт, задача на три модуля и больше. Готово: всё зелёное, опись закрыта, каждый пункт самопроверки проверен.

6. **Сдать.** Последний коммит ветки: в файле задачи пункты «Готово, когда» отмечены `[x]`; на доске фазы — ✅ и ссылка на PR; в `plan/STATUS.md` фаза → 🔄, если это первая задача фазы, или → 🔍, если последняя. Описание PR — по шаблону ниже, PR из draft в ready. `node plan/tools/plan-check.mjs` без ошибок. `main` ушёл вперёд — пересобери ветку на нём; конфликт — обычный шаг интеграции (PR-18). Готово: PR ready, CI зелёный. Ревью и исправления ведёт `/dev-loop PR <n>` в новой сессии — предложи его владельцу, если работал вне цикла. Merge — решение владельца; PR, закрытый без merge, ничего не меняет на `main`.

7. **Ответить на ревью.** Если в комментарии ревью в PR есть блокирующие находки: PR в draft (`gh pr ready <n> --undo`); каждую находку закрыть коммитом `S0-NN: review — <что>` или оспорить со ссылкой на правило; находка, упёршаяся в дизайн, — `Q-NN` или `G-NN`, как в шаге 4; «Самопроверка» на дельте; `npm run prove` зелёный, push; один ответ в PR — находка → коммит или довод по правилу; PR снова ready. Готово: на каждую блокирующую находку есть ответ в PR. Спор решает владелец; следующий круг запускает владелец или `/dev-loop`.

## Что и куда пишет исполнитель

| Что | Куда |
|---|---|
| код и тесты | `src/`, `test/`; фикстуры — `test/fixtures/<RULE-ID>/trigger/` и `pass/` |
| коммит | ветка задачи; сообщение начинается с `S0-NN:` |
| PR | GitHub, в `main`; заголовок `S0-NN · <название>`; описание — по шаблону |
| итог задачи | доска фазы: ✅ и ссылка на PR — последним коммитом ветки |
| соглашение кода, принятое по ходу | сначала проверка — тест структуры, fitness или eslint, отказ называет норму; пункт `CONVENTIONS.md` `§N.M` с областью путей — только если проверка невозможна |
| правило молчит о том, что нужно решить | `G-NN` в разделе 12 `PLAN.md` с рекомендацией и пометка в «Открытое» PR: работа идёт по рекомендации, решает владелец до merge |
| вопрос, без ответа на который дальше нельзя | `Q-NN` в разделе 11 `PLAN.md`, метка `blocked` на PR, стоп |
| вопрос о дизайне, который пришлось искать | строка в `plan/bench/questions.md`: вопрос на английском, ожидаемый ответ сразу (BN-05) |

## Отступления от задачи

Файл задачи — план, `docs/design` — правила. От плана отступить можно, от правила — нет (стоп по `AGENTS.md`). Каждое отступление видно дважды: файл задачи в той же ветке описывает сделанное, а раздел PR «Отступления от задачи» — что изменилось и почему.

| Отступление | Что делает исполнитель |
|---|---|
| сделано иначе, чем в наброске задачи: интерфейс, файлы, шаги, раскладка тестов | правит файл задачи под сделанное |
| отступление задевает другие задачи: их интерфейс, объём, `depends` | правит их файлы в той же ветке |
| пункт «Готово, когда» остаётся невыполненным | переносит его в новую задачу со ссылкой из исходной; без согласия владельца в PR задача не сдаётся |
| нужна работа сверх объёма | новая задача: файл со следующим свободным номером фазы и строка ⬜ на доске; в этой ветке этой работы нет |
| задача не нужна или поглощена другой | строка «Отменена: причина» в файле задачи, ✖ на доске |
| изменились `rules` задачи | `node plan/tools/plan-check.mjs --rules` в той же ветке |
